1. Executive Summary

CoffeeChain is a trust and traceability platform for fertilizer distribution across Tanzania's coffee-producing regions. It connects suppliers, warehouse managers, retailers, cooperatives (AMCOS), regulators, and administrators in a single digital supply chain.

What makes it trustworthy:

  • Every farmer delivery can be confirmed with an **SMS OTP** (via Briq Karibu).
  • A **verification receipt** is stored on **decentralized storage (Storacha/IPFS)** with backend fallback.
  • A **cryptographic hash** of the receipt is **anchored on Polygon Amoy** (public blockchain).
  • **Integrity monitoring** continuously compares database records against stored receipts and alerts admins on tampering.

Farmers do not log in. They are identified by Ministry of Agriculture IDs and confirm receipt via OTP only.

4. User Roles & Access Control

Authentication Model

CoffeeChain uses JWT (JSON Web Tokens) for platform users:

  1. User submits username + password → `POST /api/login/`
  2. Server returns **access token** (1 hour) + **refresh token** (7 days)
  3. Frontend stores tokens in `localStorage`
  4. All API requests include `Authorization: Bearer <access>`
  5. On expiry, frontend silently refreshes; on failure → redirect to login

Public endpoints (no JWT):

  • `POST /api/auth/register/` — self-service signup (creates pending request, not a live account)
  • `POST /api/internal/receipt-callback/` — upload-service fallback (shared secret header)

Roles

**Admin**`is_staff`Admin panelFull CRUD: users, registrations, integrity, reports
**Regulator**`Regulator`Admin panel (read-only)View users, registrations, integrity — cannot approve or edit

Authorization Enforcement

  • **Backend:** Permission classes on every viewset (`IsAdmin`, `SupplierOrAdmin`, `RegulatorOrAdmin`, etc.)
  • **Frontend:** Role-based routing to dashboards; regulator gets `readOnly: true`
  • **Data scoping:** Querysets filtered by supplier/branch; receipt access checked per transfer

6. End-to-End Supply Chain Workflow

Phase 1: Supplier Creates Inventory

  1. **Supplier** creates a `FertilizerBatch` (batch code, fertilizer type, quantity, warehouse).
  2. Batch is tied to supplier and optional warehouse location.

Phase 2: Dispatch to Branch

  1. **Supplier** creates a `Transfer` (`SUPPLIER_TO_BRANCH`, status `PENDING`).
  2. Destination: retailer or cooperative branch.
  3. **Warehouse manager** receives notification.
  4. Manager **approves** → status `DISPATCHED`, or **rejects** with reason.
  5. Destination branch notified of incoming delivery.

Phase 3: Branch Receives Stock

  1. **Retailer or AMCOS** confirms receipt → `POST /api/transfers/{id}/receive/`.
  2. Status → `RECEIVED`; `confirmed_at` timestamp recorded.
  3. Supplier and branch receive in-app notifications.

Phase 4: Distribution to Farmer

  1. **Branch** creates `Transfer` (`BRANCH_TO_FARMER`) linking farmer + batch + quantity.
  2. System validates stock (branch must have received bags first).
  3. **Cooperative:** farmer must belong to that AMCOS.
  4. **Retailer:** Ministry-verified buyers may receive subsidy discount (configurable %).
  5. OTP automatically sent to farmer's phone via Briq Karibu.

Phase 5: Farmer Confirms (OTP)

  1. Farmer receives SMS with verification code.
  2. Branch staff enters OTP in the app → `POST /api/transfers/{id}/verify_otp/`.
  3. Briq verifies code; transfer status → `VERIFIED`.

Phase 6: Trust Record Created

  1. System builds verification receipt JSON.
  2. Receipt uploaded to Storacha (or backend fallback).
  3. Cryptographic hash computed and anchored on Polygon Amoy.
  4. `BlockchainAnchor` record saved with tx hash, CID, and receipt copy in DB.

7. Farmer Verification (OTP)

Farmers are not app users. Verification is proof-of-receipt, not login.

StepAction
1Branch creates farmer distribution transfer
2`issue_distribution_otp()` calls Briq `/v1/otp/request`
3Farmer receives SMS (or call/WhatsApp on resend)
4Branch enters code → Briq `/v1/otp/verify`
5On success → verification proof recorded + blockchain anchor

Configuration: BRIQ_API_KEY, BRIQ_APP_KEY, OTP_CODE_LENGTH (default 6), OTP_EXPIRY_MINUTES (default 10).

Local dev fallback: BRIQ_OTP_LOCAL_FALLBACK=true accepts any code when Briq is unavailable.

8. Trust Layer: Receipts, Storage & Blockchain

Receipt Contents

Each verification receipt JSON includes:

  • Transfer ID, batch code, quantity, fertilizer type
  • Farmer details (Ministry ID, name, phone)
  • Branch/cooperative details
  • Verified timestamp and verifying user
  • Delivery proof CID (if photo uploaded)
  • Integrity block: `data_hash`, `payload_signature`, `content_cid`, `tx_hash`, explorer URL

Storage Strategy (Priority Order)

1. Storacha / IPFS     ← primary (decentralized, permanent)
2. Backend disk        ← fallback cache (media/receipts/)
3. PostgreSQL          ← durable fallback (BlockchainAnchor.payload.receipt)
4. IPFS gateway fetch  ← load-time recovery if only CID known

Why DB copy matters: Render's filesystem is ephemeral — disk files are lost on redeploy. The PostgreSQL copy ensures new receipts survive redeployments.

Hash & Blockchain Pipeline

payload_signature = "{batch_code}|{quantity}|{content_cid}|{transfer_id}|{verified_at}"
data_hash         = SHA-256(payload_signature)
on-chain tx       = CoffeeChainAudit.anchorTransaction(transfer_id, data_hash)

Smart Contract (`CoffeeChainAudit.sol`)

function anchorTransaction(string transactionId, string hashValue) external {
    emit TransactionAnchored(transactionId, hashValue, block.timestamp);
}
  • Stores **only the hash**, not the full receipt (privacy + cost efficiency).
  • Full receipt remains in Storacha/backend/DB.
  • Verify on [Polygonscan Amoy](https://amoy.polygonscan.com) → Logs tab → `TransactionAnchored` event.

9. Data Integrity & Tamper Detection

Manual Integrity Checks

Admin/regulator uses the Integrity panel to:

  • List all verified transfers
  • Compare database fields vs stored receipt
  • Compare DB hash vs receipt hash vs computed hash
  • View source of tampering (app user vs direct database edit)

API: GET /api/integrity/, POST /api/integrity/scan/

Automatic Tamper Detection

Django signal on Transfer post_save (signals.py):

  • Monitors changes to anchored transfers (quantity, batch, farmer, status)
  • Runs integrity check in background
  • On mismatch → in-app notification + SMS to admins

Integrity Result Statuses

StatusMeaning
`ok`Database matches receipt and hash
`mismatch`Fields or hash differ — possible tampering
`missing_receipt`Anchor exists but receipt not found
`missing_anchor`Transfer not yet verified on chain
`unchecked`Not yet compared
